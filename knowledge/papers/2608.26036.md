# Trace Integrity for LLM Data Agents: A Vision for Auditable Structured Reasoning in Real-World Systems

## One-line Summary

LLMエージェントを最終回答の正しさだけで評価するのではなく、
「その回答に至った計算過程が実行可能・再現可能・監査可能か」を
Trace Integrityとして評価すべきだと提案する研究。

## Research Question

正しい最終回答を生成したLLM Data Agentであっても、
内部の計算・SQL・操作手順が誤っているケースを
どのように検出・評価すべきか。

## Data

BIRD Mini-Devから100例を使用。

## Methodology

以下3条件を比較。

1. Direct SQL
2. Operation Summary + SQL
3. Contract-First SQL

評価指標として、

- Answer Accuracy
- Execution Success
- Trace Integrity Pass Rate
- Answer-Trace Consistency
- CAIT Rate

を使用。

CAIT:
Correct Answer / Invalid Trace

つまり、
「答えは合っているが計算過程は誤っている」
ケースを明示的に測定する。

## Main Findings

Answer AccuracyとTrace Integrityは別物だった。

Direct SQL:

- Answer Accuracy: 20.0%
- Trace Integrity Pass: 39.0%
- CAIT: 55.0%

Operation Summary + SQL:

- Answer Accuracy: 22.0%
- Trace Integrity Pass: 43.0%
- CAIT: 59.1%

Contract-First SQL:

- Answer Accuracy: 24.0%
- Trace Integrity Pass: 40.0%
- CAIT: 45.8%

## Evidence

- 正答であっても、その計算Traceがinvalidであるケースが多数存在する。
- CAIT Rateは3方式すべてで高い。
- Execution Contractとして、schema、operator plan、assumption、
  executable query、verification status、final answerとの対応を
  構造化することを提案している。
- 失敗したTraceをRegression Testとして再利用することも提案されている。

## Limitations

- BIRD Mini-Dev 100例のみ。
- 使用モデルは1モデル。
- 固定されたprompt / execution環境。
- deterministic validatorは完全なsemantic equivalenceを保証しない。

## Interpretation

ArxivResearchAgentのようなAIエージェントでは、
「生成されたKnowledgeがもっともらしいか」だけでなく、

Input
→ Evidence
→ Interpretation
→ Insight
→ Hypothesis

という変換関係そのものを監査可能なartifactとして保存する設計が重要になる。

これは今回の
Structured Markdown + Validation + Git
という設計思想と非常に整合する。

## Potential Applications

- AI Agent生成物の自動検証
- データマート開発Agentの監査
- Research Agentのprovenance管理
- backtest Agentの再現性検証
- agent outputのregression test化

## Research Questions Generated

- Research Agent向けCAITに相当する指標を定義できないか？
- Evidenceは正しいがInsightへの推論が誤っているケースをどう測るか？
- Git履歴をTrace Integrity artifactとして利用できるか？
